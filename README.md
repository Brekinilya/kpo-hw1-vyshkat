# ВышКат — учёт парка кикшеринга

ДЗ-1 по КПО: доменная модель, консольное приложение, SOLID, DI-контейнер, юнит-тесты.

## Запуск

Нужен Python 3.12 или новее.

Windows:

```
py -3.12 -m venv .venv
.venv\Scripts\python -m pip install -e ".[dev]"
.venv\Scripts\python -m vyshkat
```

Linux / macOS:

```
python3 -m venv .venv
.venv/bin/python -m pip install -e ".[dev]"
.venv/bin/python -m vyshkat
```

Зависимость приложения одна — `dependency-injector`. Остальное (`pytest`, `pytest-cov`, `ruff`, `mypy`) ставится через `[dev]` и нужно только для тестов и проверки стиля.

## Как пользоваться

Приложение интерактивное, данные вводятся с консоли или загружаются из JSON-файла. Демо-данных в коде нет.

```
1. Принять технику (с техосмотром)
2. Поставить вещь на баланс
3. Загрузить поставку из JSON-файла
4. Отчёт: число единиц и суточная энергия
5. Техника для новичков
6. Инвентарная ведомость
0. Выход
```

- **1** — выбор вида (электросамокат, велосипед, электровелосипед), затем наименование, инвентарный номер, простота для новичка (1–10), износ по итогам осмотра (0–100 %). Для электротранспорта дополнительно спрашивается суточный расход энергии. Дальше техника проходит техосмотр и либо попадает в парк, либо получает отказ с причиной.
- **2** — шлем, док-станция или зарядный шкаф. Вещи ставятся на баланс без техосмотра, расход энергии спрашивается только у док-станции и шкафа.
- **3** — путь к файлу поставки (кавычки вокруг пути допустимы). По каждой записи выводится результат: `vehicles, запись 4: [отказ] ... — износ 55% выше допустимых 40%`.
- **4–6** — отчёты.

Если вместо числа введён текст, вопрос повторяется. Дробные числа принимаются и с точкой, и с запятой. Ошибки модели (простота 11, занятый номер, пустое наименование) выводятся как отказ, приложение при этом не падает. Конец ввода (Ctrl+Z, Enter в Windows или Ctrl+D) завершает работу так же, как пункт 0.

### Формат файла поставки

Пример лежит в [samples/delivery.json](samples/delivery.json):

```json
{
  "vehicles": [
    {"type": "scooter", "name": "ВышКат Lite", "inventory_number": 101,
     "simplicity": 8, "wear_percent": 10, "daily_energy_kwh": 0.45}
  ],
  "things": [
    {"type": "helmet", "name": "Шлем M", "inventory_number": 501},
    {"type": "dock", "name": "Док-станция у Покровки", "inventory_number": 601,
     "daily_energy_kwh": 1.2}
  ]
}
```

Виды: `scooter`, `bicycle`, `ebike` для техники; `helmet`, `dock`, `cabinet` для вещей. Поля записи совпадают с параметрами конструктора соответствующего класса. Если поля не хватает или есть лишнее, это будет сказано явно: `вид «Электросамокат» — не хватает полей: simplicity; лишние поля: simplicty`. Если файл не читается или его структура сломана (не JSON, не UTF-8, раздел не список), поставка отклоняется целиком и в парк ничего не попадает.

### Сценарий для демонстрации

1. `3` → `samples/delivery.json`: принято 8 из 9, электровелосипед с износом 55 % не прошёл техосмотр.
2. `4`: 4 единицы техники, 4 вещи, 6.50 кВт·ч в сутки (велосипед и шлемы энергию не потребляют).
3. `5`: в списке №101, №201, №302; самокат №102 с простотой 5 не попадает.
4. `6`: ведомость всех 8 единиц по возрастанию номера.
5. `1`: принять самокат с износом 50 % и получить отказ, затем повторить с номером 101 и получить «номер уже занят».

## Структура

```
src/vyshkat/
  domain/                 модель, ни от чего снаружи не зависит
    interfaces.py         IInventory, IEnergyConsumer
    inventory.py          InventoryItem — общая реализация номера и наименования
    vehicles.py           Vehicle, ElectricVehicle, Bicycle, Scooter, ElectricBike
    things.py             Thing, PoweredThing, Helmet, DockStation, ChargingCabinet
    service_center.py     IServiceCenter, ServiceCenter, InspectionResult
    park.py               Park, FleetReport
    validation.py         проверки значений
    errors.py             DomainError, DuplicateInventoryNumberError
  application/
    catalog.py            Catalog — ключ вида → класс
    intake.py             Intake — приёмка: создать объект по виду и поставить в парк
  ui/
    console.py            ConsoleApp — меню
    delivery_file.py      DeliveryFileLoader — поставка из JSON
  container.py            DI-контейнер, единственное место сборки зависимостей
  __main__.py
samples/delivery.json
tests/
```

Зависимости направлены внутрь: `ui` → `application` → `domain`.

## Модель и логика решений

```
IInventory                          IEnergyConsumer
  └─ InventoryItem                         │
       ├─ Vehicle                          │
       │    ├─ Bicycle                     │
       │    └─ ElectricVehicle ────────────┤
       │         ├─ Scooter                │
       │         └─ ElectricBike           │
       └─ Thing                            │
            ├─ Helmet                      │
            └─ PoweredThing ───────────────┘
                 ├─ DockStation
                 └─ ChargingCabinet
```

- **Энергия — отдельный интерфейс.** Деление «техника / вещь» и деление «потребляет энергию / нет» не совпадают: велосипед и шлем энергию не потребляют, а электросамокат и док-станция — да. Поэтому [`IEnergyConsumer`](src/vyshkat/domain/interfaces.py) подключается там, где он нужен, а не висит на базовом классе.
- **[`IInventory`](src/vyshkat/domain/interfaces.py) — это номер, наименование и вид.** Состав задаёт главный потребитель интерфейса — инвентарная ведомость: она выводит все три поля и работает только через интерфейс. [`InventoryItem`](src/vyshkat/domain/inventory.py) — общая реализация, чтобы не дублировать хранение номера и наименования.
- **Абстрактные базы.** Вид (`kind`) задаёт только конкретный класс. Поэтому `Vehicle`, `ElectricVehicle`, `Thing`, `PoweredThing` абстрактные, и создать «просто транспорт» без вида нельзя.
- **Модель всегда валидна.** Конструкторы проверяют значения ([validation.py](src/vyshkat/domain/validation.py)), свойства только для чтения, инвентарный номер обязателен и задаётся один раз. Отсекаются `nan`, `inf`, `True` вместо числа, `101.0` вместо целого.
- **Техосмотр.** [`ServiceCenter`](src/vyshkat/domain/service_center.py) отклоняет технику с износом выше порога (по умолчанию 40 %) и возвращает решение с причиной. Через техосмотр проходит только техника, поэтому `inspect` принимает `Vehicle`.
- **Номера уникальны по всему парку**, общие для техники и вещей. [`Park`](src/vyshkat/domain/park.py) проверяет номер до техосмотра: занятый номер — это отказ, и осматривать технику незачем.
- **Правило для новичков** — `Vehicle.is_suitable_for_beginners()`: простота не ниже `BEGINNER_MIN_SIMPLICITY = 6`.
- **Приёмка одна на оба способа ввода.** Меню и JSON-файл отдают в [`Intake`](src/vyshkat/application/intake.py) ключ вида и поля. `Intake` находит класс в каталоге, создаёт объект и передаёт его в парк. Ни меню, ни загрузчик не дублируют правила модели.
- **Ошибки.** Нарушение правил модели — [`DomainError`](src/vyshkat/domain/errors.py), и приёмка перехватывает только его. Ошибка в самом коде (например, `TypeError` внутри конструктора) не превращается в «пользователь ввёл что-то не то», а падает как есть.
- **Отчёты — неизменяемые снимки.** `tuple`, `frozen`-датаклассы. Каталог хранится в `MappingProxyType`, поэтому изменить его после создания нельзя.

## SOLID

**S — единственная ответственность.** У каждого класса своя причина для изменений. `ServiceCenter` меняется, если меняется правило техосмотра. `Park` — если меняется учёт. `Intake` — если меняется порядок приёмки. `ConsoleApp` — если меняется диалог. `DeliveryFileLoader` — если меняется формат файла. Например, новое правило осмотра не затрагивает ни меню, ни парк.

**O — открытость/закрытость.** Новый вид техники или вещи — это новый класс и одна строка в [`DEFAULT_CATALOG`](src/vyshkat/application/catalog.py). Меню строится по каталогу, а парк, отчёты, техосмотр и загрузка из файла работают с базовыми типами и интерфейсами, поэтому их менять не нужно. Это закреплено тестом `test_new_vehicle_kind_needs_only_a_class_and_a_catalog_entry`: вид `Segway` объявлен прямо в тесте и проходит приёмку без правок кода.

**L — подстановка Лисков.** Любой наследник `Vehicle` принимается в `admit_vehicle` и `inspect`, любой `IEnergyConsumer` учитывается в энергии. Наследники не усиливают предусловия и не меняют смысл свойств: они добавляют только вид или расход энергии.

**I — разделение интерфейсов.** Интерфейсы маленькие: у `IInventory` три свойства, у `IEnergyConsumer` одно, у `IServiceCenter` один метод. Велосипед и шлем не обязаны реализовывать энергию. `Park.daily_energy_kwh` зависит только от `IEnergyConsumer`, ведомость — только от `IInventory`.

**D — инверсия зависимостей.** `Park` получает `IServiceCenter` через конструктор и не знает, какая реализация за ним стоит. Реализации выбираются в одном месте — в [container.py](src/vyshkat/container.py). Консоль получает функции чтения и записи (по умолчанию `input` и `print`), поэтому её можно тестировать без настоящей консоли.

## Обязательные вопросы

### 1. Какой принцип SOLID применён наиболее явно и где

DIP. [`Park`](src/vyshkat/domain/park.py) зависит от абстракции [`IServiceCenter`](src/vyshkat/domain/service_center.py), конкретный `ServiceCenter` подставляет DI-контейнер ([container.py](src/vyshkat/container.py)). Благодаря этому решение о приёмке подменяется без единой правки в `Park`: в юнит-тестах передаётся fake или mock, в интеграционном тесте провайдер контейнера переопределяется через `override`.

### 2. Какой принцип сознательно ограничен и почему это приемлемо

- **SRP в `Park`.** Парк одновременно хранит объекты, проверяет уникальность номеров и считает отчёты. Отдельные репозиторий и сервис отчётов при хранении в памяти в двух списках были бы церемонией без пользы. Если появится база данных, хранение выносится в репозиторий, а интерфейс `Park` для остального кода не меняется.
- **OCP в консольной форме.** Вопросы при приёме техники перечислены в `ConsoleApp._admit_vehicle` явно: наименование, номер, простота, износ и расход энергии, если вид реализует `IEnergyConsumer`. Новый вид с теми же полями добавляется без правок консоли, а вид с новым полем (например, максимальной скоростью) потребует добавить в форму один вопрос. Строить форму рефлексией по сигнатуре конструктора можно, но код стал бы заметно сложнее ради одного гипотетического поля. Загрузка из JSON этого ограничения не имеет: она передаёт в конструктор любые поля.

### 3. Что сломается при расширении

- **Новый вид транспорта** (например, электрический сегвей): класс-наследник `ElectricVehicle` с `kind = "Сегвей"` и строка `"segway": Segway` в каталоге. Меню, файл поставки, техосмотр, отчёт по энергии и список для новичков подхватят его сами. Ничего не сломается. Единственный случай, когда придётся править консоль, — вид с новым полем (см. вопрос 2).
- **Сотрудники.** По условию сотрудники на баланс не ставятся, поэтому они не реализуют `IInventory` и в `Park` не попадают. Это отдельный модуль (например, `domain/staff.py`) и новые пункты меню. Существующие классы не меняются, отчёты по числу единиц и энергии остаются прежними. Меню дополняется новыми пунктами в `ConsoleApp._actions`, контейнер — новыми провайдерами.
- **Склад запчастей.** Запчасти учитываются партиями с количеством, а не поштучно, поэтому партия — не `IInventory` и в `Park` её класть не надо. Склад — отдельный агрегат рядом с парком. Сам стеллаж или шкаф склада, если его нужно инвентаризировать, становится обычным наследником `Thing`. Сломается одно: сейчас уникальность инвентарных номеров проверяет `Park` у себя внутри. Если номера должны быть общими для парка и склада, эту проверку придётся вынести в отдельный реестр номеров, которым будут пользоваться оба.
- **Новое правило техосмотра** (например, проверка батареи у электротранспорта): меняется только `ServiceCenter`, или пишется новая реализация `IServiceCenter` и подставляется в контейнере. `Park`, приёмка и интерфейс не меняются.

### 4. Какой тест фиксирует техосмотр и правило «для новичков», как подменяется зависимость

Техосмотр:
- [test_service_center.py](tests/test_service_center.py): `test_vehicle_at_wear_limit_passes_inspection` и `test_worn_vehicle_is_rejected_with_reason` фиксируют само правило (40 % — проходит, 41 % — отказ с причиной).
- [test_park.py](tests/test_park.py): `test_vehicle_rejected_by_service_center_stays_out` — парк не принимает технику, если осмотр отказал. `test_park_follows_service_center_decision` — парк вызывает `inspect` ровно один раз с этой техникой и возвращает решение как есть. `test_duplicate_number_is_refused_before_inspection` — при занятом номере до осмотра дело не доходит.
- [test_container.py](tests/test_container.py): `test_service_center_is_replaced_through_container` — подмена через DI-контейнер.

Правило для новичков:
- [test_items.py](tests/test_items.py): `test_beginner_rule_uses_simplicity_threshold` — граница: 5 не подходит, 6 подходит.
- [test_park.py](tests/test_park.py): `test_beginner_list_contains_only_simple_vehicles` — список парка.
- [test_console.py](tests/test_console.py): `test_beginner_list_shows_only_simple_vehicles` — то же через меню.

Подмена зависимости сделана тремя способами:
- **stub/fake** — [`FakeServiceCenter`](tests/support.py) реализует `IServiceCenter`, возвращает заранее заданное решение и запоминает, что ему передали;
- **mock** — `create_autospec(IServiceCenter, instance=True)`: проверяем вызов через `assert_called_once_with`;
- **через контейнер** — `with container.service_center.override(fake): park = container.park()`. Парк, собранный контейнером, получает подменённый техосмотр.

### 5. Что сделал ИИ, что сделал я

ИИ-ассистент использовался как инструмент для поиска ошибкок. За проектирование и основное написание кода отвечаю я.

**Что изменил ИИ:**
- Нашел список ошибок в проекте, исправил по моему запросу. В результате:
  - приёмка больше не выдаёт ошибки программы за ошибки ввода: ловится только `DomainError`, а не любой `TypeError` / `ValueError`;
  - каталог видов стал неизменяемым;
  - методы парка единообразно возвращают `tuple`;
  - вид перенесён в `IInventory`, и ведомость работает через интерфейс;
  - базовые классы стали абстрактными;
  - сообщения об ошибках только на русском, с номером записи файла и списком недостающих и лишних полей.

- по моему запросу проверил проект по списку типичных ошибок и внёс исправления.

**Что сделано мной:**
- предложил инструменты и исходный вариант архитектуры: слои `domain` / `application` / `ui`, интерфейсы `IInventory` и `IEnergyConsumer`, приёмку через `Intake` и каталог видов;
- написал первую версию кода, тестов и README;
- утвердил предметные правила: техосмотр по износу с порогом 40 %, инвентарный номер вводит оператор, правило для новичков базовое (простота ≥ 6) без усложнений, чтобы не уйти в overengineering;

## Тесты и стиль кода

```
.venv\Scripts\pytest --cov
.venv\Scripts\ruff check src tests
.venv\Scripts\ruff format --check src tests
.venv\Scripts\mypy src tests
```

На Linux / macOS вместо `.venv\Scripts\` — `.venv/bin/`.

Порог покрытия 60 % задан в `pyproject.toml`, при меньшем покрытии `pytest --cov` падает. Текущее покрытие около 98 %, не покрыт только `__main__.py`.

Тесты проверяют поведение, а не устройство классов: правила модели, решения техосмотра, отчёты, разбор файла поставки (включая битые файлы) и сценарии меню. Для меню ввод подаётся списком ответов.

Стиль проверяется `ruff` (линтер и форматтер) и `mypy` в строгом режиме.
